## Punton 1:
Git es un sistema de control de versiones distribuido que rastrea y registra los cambios en los archivos de un proyecto a lo largo del tiempo. Funciona tomando "fotografías" (commits) del estado del código en momentos específicos, lo que permite navegar por su historial con total precisión.

El problema principal que resuelve es el caos de la colaboración concurrente y la gestión del código fuente. En un entorno de desarrollo, elimina directamente los siguientes obstáculos:

Pérdida de historial y versiones: Acaba con la necesidad de duplicar carpetas o renombrar archivos manualmente (index_final_v3.html). Mantiene un registro cronológico inmutable de quién cambió qué, cuándo y por qué (trazabilidad).

Conflictos de sobreescritura: Permite que múltiples desarrolladores trabajen en el mismo proyecto, e incluso en el mismo archivo, de forma simultánea. Git gestiona la integración (merge) de esos cambios y alerta sobre los conflictos antes de que el trabajo de alguien sea sobrescrito por error.

Riesgo al experimentar: Mediante el sistema de ramas (branches), permite crear entornos de trabajo aislados para desarrollar nuevas características o probar correcciones sin afectar la línea base de código estable (producción).

Dependencia de un servidor único: Al ser un sistema distribuido, cada desarrollador tiene una copia local completa de todo el repositorio y su historial. Esto significa que se puede trabajar sin conexión a internet y, si el servidor principal cae, cualquier copia local sirve como respaldo total

## Punto 3

Una nube de repositorios, también conocida como plataforma de alojamiento de código, es un servicio en línea que permite guardar, gestionar y compartir proyectos de desarrollo de software utilizando sistemas de control de versiones como Git. Su función principal es actuar como un servidor central en internet donde los programadores suben su código, llevan un historial detallado de cambios y colaboran con otros desarrolladores desde cualquier lugar del mundo.
Estas plataformas van mucho más allá del simple almacenamiento de archivos en la nube. Integran herramientas fundamentales para el trabajo en equipo, como la creación de ramas para desarrollar funciones sin afectar el código principal, la revisión de cambios antes de fusionarlos, el seguimiento de errores mediante tickets y la automatización de pruebas y despliegues cada vez que se actualiza el proyecto.
Además de GitHub, existen varias alternativas destacadas en el mercado con distintos enfoques. La primera es GitLab, una plataforma muy completa que se distingue por integrar de forma nativa herramientas avanzadas de automatización y seguridad, además de permitir que las empresas la instalen en sus propios servidores privados. La segunda es Bitbucket, desarrollada por Atlassian, que está muy orientada a entornos corporativos y destaca por su integración directa con otras herramientas de gestión como Jira y Trello.
Una tercera alternativa es Azure Repos, que forma parte del ecosistema Azure DevOps de Microsoft y ofrece repositorios privados ilimitados junto con una fuerte integración con herramientas empresariales y de nube de la misma compañía. Por último, también existen opciones de código abierto como Gitea o Forgejo, ideales para desarrolladores u organizaciones que prefieren montar su propia nube de repositorios ligera en un servidor propio para tener control total sobre sus datos

## Punto 4

Un Commit es como tomar una fotografía o guardar un punto de control de tu proyecto en un momento exacto. Cada vez que guardas cambios importantes en tus archivos, creas un commit con un mensaje corto que explica qué hiciste, lo que permite volver a ese punto exacto en el futuro si algo sale mal. Por ejemplo, imagina que estás creando una página web, terminas de diseñar el formulario de contacto y haces un commit con el mensaje "Agrega formulario de contacto funcional" para dejar registrado ese avance.
Una Branch (Rama) es una línea de desarrollo independiente que se desprende del proyecto principal. Sirve para trabajar en nuevas funciones o corregir errores sin arriesgar el código que ya funciona bien en la versión oficial. Por ejemplo, si tu aplicación ya está publicada en la rama principal y quieres probar un modo oscuro, creas una rama llamada "modo-oscuro", haces allí todos tus experimentos y, si algo falla, la aplicación original sigue intacta.
Un Merge (Fusión) es la acción de unir el trabajo de una rama con otra para integrar los cambios. Una vez que terminas de desarrollar y probar una función en una rama secundaria, la fusionas con la rama principal para que forme parte del proyecto oficial. Siguiendo el ejemplo anterior, cuando el diseño del modo oscuro está listo y sin errores, haces un merge desde la rama "modo-oscuro" hacia la rama principal para que todos los usuarios puedan verlo.
Pull y Push son los comandos que sincronizan tu computadora con el repositorio en la nube. Hacer Push significa empujar o subir tus commits locales hacia la nube para que otros los vean, mientras que hacer Pull significa traer o descargar los cambios nuevos que tus compañeros subieron a la nube hacia tu computadora. Por ejemplo, al empezar tu jornada haces un pull para descargar el código que tu equipo avanzó anoche, y al terminar tu tarea del día haces un push para subir tu trabajo.
Un Pull Request (PR) es una petición formal que haces a tu equipo para que revisen tu código antes de fusionarlo con la rama principal. No es una función propia de Git, sino una herramienta de plataformas como GitHub o GitLab que abre un espacio de debate donde otros programadores pueden comentar tus líneas de código, pedir correcciones y aprobar los cambios. Por ejemplo, subes tu rama con un nuevo sistema de pagos y abres un PR para que el líder técnico revise que no haya fallos de seguridad antes de integrarlo al proyecto.
Clone (Clonar) es el proceso de descargar una copia completa de un repositorio desde la nube hacia tu computadora por primera vez. A diferencia de descargar un archivo comprimido normal, clonar trae todos los archivos junto con todo el historial de commits, las ramas existentes y la conexión lista para empezar a trabajar. Por ejemplo, cuando entras a trabajar en una empresa nueva, te pasan el enlace del proyecto en GitHub y ejecutas el comando clone para tener todo el código y su historial en tu equipo.
Origin y Upstream son los nombres que se usan para identificar diferentes ubicaciones de un repositorio en la nube. Origin es el nombre por defecto que recibe tu propio repositorio remoto (el que clonaste o creaste en tu cuenta), mientras que Upstream se refiere al repositorio original del cual hiciste una copia (fork), generalmente administrado por otra persona u organización. Por ejemplo, si quieres colaborar en un proyecto público de código abierto, primero haces una copia en tu cuenta (ese es tu Origin) para subir tus cambios, pero configuras la dirección del proyecto original como Upstream para poder descargar las actualizaciones oficiales que hagan sus creadores

## Punto 5

Crear ramas en un proyecto de software es una práctica fundamental porque permite aislar el trabajo nuevo del código estable que ya está funcionando. En lugar de modificar directamente la versión oficial del proyecto (conocida habitualmente como rama principal o main), los desarrolladores crean una copia paralela donde pueden escribir, probar y corregir código con total libertad. Si ocurre un error grave durante el desarrollo, este queda contenido dentro de esa rama y nunca afecta la experiencia de los usuarios finales ni interrumpe el funcionamiento del sistema principal.
En el trabajo individual, las ramas ofrecen una enorme ventaja organizativa y de seguridad. Permiten experimentar con ideas arriesgadas, probar nuevas librerías o reescribir partes complejas de un programa sabiendo que, si el experimento no funciona como se esperaba, basta con borrar esa rama para volver al estado limpio original sin dejar archivos basura. Además, ayudan a mantener el orden cuando un mismo programador atiende varias tareas a la vez, ya que puede tener una rama dedicada a una nueva función y otra rama distinta para corregir un error urgente, cambiando entre ambas sin mezclar códigos incompletos.
En el trabajo en equipo, las ramas son la base de la colaboración simultánea y ordenada. Gracias a ellas, diez o cien programadores pueden trabajar sobre el mismo proyecto al mismo tiempo sin sobrescribir ni dañar el trabajo de los demás, ya que cada persona o subequipo desarrolla su tarea en su propia rama independiente. Asimismo, facilitan el control de calidad antes de integrar los cambios, pues permiten que otros compañeros revisen el código de una rama específica, ejecuten pruebas automáticas y aprueben las mejoras antes de fusionarlas con el proyecto oficial

## Punto 6

GitFlow es un modelo de gestión y organización de ramas para Git diseñado para proyectos con ciclos de lanzamiento de software estructurados y predecibles. Funciona como una guía estricta que define qué ramas se deben crear y cómo deben interactuar entre sí para mantener el código ordenado, facilitando el desarrollo en paralelo y la entrega continua.

Estructura de las ramas en GitFlow

El modelo se divide en dos ramas permanentes a largo plazo y tres tipos de ramas temporales de corta duración:
• Rama master (o main): Es la rama permanente que contiene el código oficial que ya está en producción. Todo el código en esta rama está completamente probado, es estable y representa las versiones públicas que usan los usuarios finales. Cada vez que se fusiona algo aquí, se le asigna una etiqueta de versión (como v1.0 o v2.0).
• Rama develop: Es la rama permanente donde se integra el trabajo diario de todos los desarrolladores. Funciona como el área de preparación principal para la próxima versión del software. Contiene las últimas funciones completadas que están esperando a ser empaquetadas para el siguiente lanzamiento.
• Ramas feature: Son ramas temporales que se crean para desarrollar una nueva funcionalidad específica. Nacen siempre a partir de develop y, una vez que la función está terminada y revisada, se fusionan de vuelta en develop para luego ser eliminadas. Nunca interactúan directamente con master.
• Ramas release: Son ramas temporales que se abren cuando develop ya acumuló suficientes funciones y se decide preparar un nuevo lanzamiento oficial. En esta rama solo se permiten correcciones de errores menores, pulido de detalles y documentación para esa versión específica. Una vez lista, se fusiona tanto en master (para publicarse) como en develop (para guardar los arreglos de errores), y luego se borra.
• Ramas hotfix: Son ramas temporales de emergencia que se abren directamente desde master cuando se detecta un fallo crítico en la versión de producción que debe corregirse de inmediato. Permiten solucionar el problema urgente sin interrumpir el trabajo de las funciones nuevas que se están haciendo en develop.
